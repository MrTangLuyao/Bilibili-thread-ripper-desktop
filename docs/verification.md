## 0.9.1.1-d5 不限客户端版本、后台监视和维护窗口

日期：2026-09-16。没有修改共享下载核心；桌面传输层只加了连续失败后暂停加速的保护。

已查明的原因：

- 客户端日志显示，官方平时通过 `%APPDATA%\bilibili\resource` 里的缓存包更新（Patch info、Use main cache），Program Files 里的入口不变。9 月 15 日改动缓存包时客户端报 `Start error, code: 012`，说明缓存包有官方校验，d5 不碰它。客户端内置的完整安装包更新通道当时显示最新是 1.9.0，实际不会触发。
- 本机 d4 日志停在 closing 的原因：用 Node 创建的父进程被强制结束后，它非 detached 启动的子进程会被一起结束，子进程再启动的进程不会（本机实验结果）。客户端日志显示，16:27:11 的更新和 16:27:23 的卸载之后，客户端分别在 16:27:16 和 16:27:26 被重新打开，说明后台 PowerShell 都执行完了，只是窗口被结束了。
- 新增的回归测试用模拟客户端创建与 Electron 相同标志的作业对象，再由维护脚本真的把模拟客户端关掉。d4 的程序在这个测试中复现了一模一样的日志（停在 closing，后台照样装完并重新打开）；d5 通过。

自动化测试（本机 Windows PowerShell 5.1、.NET Framework 4 编译、Node 测试、Headless Chrome）：

- 21 项 Node 测试和浏览器回归全部通过。
- 客户端版本：99.0.0、2.0.0 等未知版本只要入口结构正常就能接入；`main` 指向子目录时前缀路径正确；没有入口、入口是编译后的文件、入口路径越界、包名不是 bilibili 时不改文件；BOM 和 "use strict" 保持在最前；BTR 引导脚本出错时官方入口照常执行。
- d4 格式的入口前缀被识别为需要修复，并从原始备份重新生成。
- 模拟官方完整安装包换成 1.19.0 后，重新接入离线完成，只保留新客户端的原始备份，旧备份删除；再卸载能精确还原 1.19.0 的原始字节。认不出结构的客户端，修复和卸载都不改文件。
- 维护窗口：更新和卸载在“客户端被关闭”的条件下都完整记录到 complete 和 Worker exit 0，并重新打开模拟客户端。
- d4 安装包里的 `install.ps1`（也就是 d4 用户在客户端内升级时实际运行的脚本）能安装本地 d5 包，装好后状态为当前版本。
- 监视程序：命令行参数经过 Windows 解析后不变；只删除指向自己安装目录的启动项；任务管理器里关闭启动项后不运行；能识别档案头里的 BTR；维护锁被占用时等待；拒绝过的文件不再询问；认不出结构时只提示。端到端测试中，它发现模拟客户端被覆盖后弹出提示，点击“重新接入 BTR”后通过独立窗口完成接入并重新打开客户端；点击“这次不用”后文件保持不变并记住选择；删掉 current.json 后自己退出。测试没有传 `--register`，测试前后都确认真实的开机启动项里没有 BTR。
- 客户端主进程只在监视程序哈希正确时启动它，使用 detached；哈希不对或旧部署没有哈希时不启动。
- 浏览器回归：连续 6 次加速失败后，这个窗口暂停加速，之后的请求直接走原生下载，不再重复失败。
- 所有涉及文件的测试都用临时目录里的模拟客户端，测试前后检查真实客户端 app.asar 哈希不变。

真实客户端上的只读检查：

- 用客户端自带的 Electron 22.3.27，在内存里给 1.18.0 官方原始备份打 d5 补丁：识别入口为 `index.js`，新入口能通过语法检查，官方代码原样保留在前缀之后，`main` 目录文件不变。没有写入任何文件。
- d5 的状态检查报告本机客户端结构可识别，当前部署是 d4、需要更新，真实 app.asar 哈希不变。
- 删除了 `%APPDATA%\bilibili\resource\btr-desktop-backups`（9 月 15 日早期测试遗留，内容与 Program Files 中的原始备份相同，没有程序引用）。

尚未验证，不能说成已完成：

- 没有把 d5 装到本机真实客户端，也没有在真实客户端里从 d4 点击更新到 d5。d4 点更新时窗口仍会消失，这是 d4 自身的问题，只能在后台完成。
- 没有在真实客户端上遇到官方热更新到新版本，也没有真实重装官方安装包来触发监视程序。
- 没有在 d5 下做真实视频播放验收。
